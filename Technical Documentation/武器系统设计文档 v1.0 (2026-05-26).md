## 2. 现状分析（重构前）

### 2.1 当前架构

```
IWeapon (abstract class)
├── AK
├── MP5
├── AWP
├── DE
├── ShotGun
└── Laser
```

### 2.2 当前实现特点

| 武器类型  | 特点          | 代表武器                   |
| ----- | ----------- | ---------------------- |
| 全自动武器 | 循环开火音效、持续射击 | AK、MP5、Laser           |
| 半自动武器 | 单次射击、无循环音效  | AWP、DE、ShotGun         |
| 特殊武器  | 非常规攻击逻辑     | Laser（无子弹）、ShotGun（散射） |

### 2.3 现有代码结构问题

#### 问题1：命名误导

`IWeapon` 实际上是 abstract class，不是 interface

```csharp
public abstract class IWeapon : ViewController { ... }
```

#### 问题2：代码重复严重

| 重复方法                    | 重复次数 | 问题描述                    |
| ----------------------- | ---- | ----------------------- |
| `Reload()`              | 6 次  | 换弹逻辑完全相同                |
| `TryPlayDryFireClick()` | 6 次  | 空弹夹点击音效逻辑完全相同           |
| `SwitchFromSet()`       | 6 次  | 武器切换时的状态重置逻辑大量重复        |
| `SwitchToSet()`         | 6 次  | 武器切换回时的初始化逻辑大量重复        |
| `keepAttacking()`       | 6 次  | 弹药检查和 reload 文本显示逻辑高度相似 |

#### 问题3：职责不清

- 全自动武器的循环音效管理与半自动武器混在一起
- 特殊武器的攻击逻辑（Laser的BoxCast、ShotGun的散射）直接写在各自类中
- 升级系统和元素效果没有预留扩展接口
- 武器自身的换弹函数没有被调用，目前使用gunclip，但换弹结束事件也没被订阅过

#### 问题4：扩展性差

- 无法动态切换攻击模式
- 添加新武器类型需要复制大量重复代码
- 升级系统需要从零开始实现

## 3. 修改目的

### 3.1 核心目标

1. **消除代码重复**：提取通用逻辑到基类，提高可维护性
2. **清晰分类**：区分全自动/半自动武器，明确职责边界
3. **支持升级系统**：为武器等级提升和形态变化提供基础架构
4. **支持元素效果**：为冰/火/毒等属性效果提供扩展接口
5. **提高扩展性**：便于添加新武器类型和攻击模式

### 3.2 重构收益预估

| 指标        | 重构前    | 重构后   | 改善幅度 |
| --------- | ------ | ----- | ---- |
| 代码重复率     | \~60%  | \~15% | -75% |
| 添加新武器工作量  | 3-4 小时 | 30 分钟 | -87% |
| 升级系统实现复杂度 | 高      | 低     | 大幅降低 |

## 4.3.1 武器系统核心决策

> **状态说明**：✅ 已实施 | 🔄 进行中 | 📋 计划中

#### 决策1：武器分类 - 双层继承架构 ✅

**背景**：初期所有武器直接继承 IWeapon，导致全自动和半自动武器逻辑混杂，难以维护

**现状实现**：

- `AutomaticWeapon` 基类：处理全自动武器的循环射击逻辑（AK、MP5、Laser）
- `SemiAutomaticWeapon` 基类：处理半自动武器的单次射击逻辑（AWP、DE、ShotGun）

**方案对比**：

| 方案    | 双层继承（Automatic/SemiAutomatic） | 单层继承      | 纯策略模式 |
| ----- | ----------------------------- | --------- | ----- |
| 代码复用  | 高（自动/半自动各自复用）                 | 中（部分逻辑重复） | 高     |
| 逻辑清晰  | 高（职责明确）                       | 中（逻辑混杂）   | 高     |
| 实现复杂度 | 中                             | 低         | 高     |
| 扩展性   | 中                             | 低         | 高     |

**采用原因**：
- 全自动武器与半自动武器职责分离，逻辑清晰
- 同类武器共享基类逻辑，减少重复代码
- 平衡复杂度，避免过度设计

***

#### 决策2：音效管理 - 集中式 AudioManager ✅

**背景**：初期每把武器挂载独立 AudioSource，导致资源浪费和管理困难

**现状实现**：

- 每把武器使用独立的 AudioSource 组件
- 通过统一的接口调用音效播放

**方案对比**：

| 方案    | 每武器独立 AudioSource（当前） | 集中式 AudioManager（计划） |
| ----- | --------------------- | -------------------- |
| 资源占用  | 高（6-12 个）             | 低（2-3 个）             |
| 可控性   | 低（分散管理）               | 高（统一管理）              |
| 扩展性   | 低（每个武器单独处理）           | 高（统一接口）              |
| 实现复杂度 | 低                     | 中                    |

**采用原因（当前方案）**：
- 实现简单，便于快速开发
- 每个武器的音效独立，便于调试定位
- 每把武器可独立设置音量、3D位置等参数

**未来规划**：重构为集中式 AudioManager，便于统一控制和进一步扩展

***

#### 决策3：弹药系统 - 组合模式（GunClip） ✅

**背景**：初期弹药管理逻辑直接写在武器类中，导致武器类职责过重，难以维护

**现状实现**：

- 独立的 `GunClip` 类管理弹药逻辑
- `AttackInterval` 管理攻击间隔
- `BloodBank` 管理血液消耗

**方案对比**：

| 方案    | 组合模式（GunClip 独立类） | 继承模式        | Mixin/特质模式 |
| ----- | ----------------- | ----------- | ---------- |
| 职责分离  | 高（弹药逻辑独立）         | 低（混杂在武器中）   | 高          |
| 复用性   | 高（所有武器共用）         | 低（每个武器重复实现） | 高          |
| 扩展性   | 高（可替换不同弹夹类型）      | 低（需修改武器类）   | 中          |
| C# 支持 | ✅ 原生支持            | ✅ 原生支持      | ❌ 需第三方库    |

**采用原因**：
- 武器专注攻击逻辑，弹夹专注弹药管理，职责分离
- 可动态更换弹夹类型（如扩容弹夹、特殊弹药）
- 弹夹逻辑可独立测试

***

#### 决策4：武器切换机制 - 接口解耦 ✅

**背景**：如何实现武器系统与玩家控制的解耦？

**现状实现**：

| 耦合度   | 低（接口解耦）      | 高（强耦合）    | 低                 |
| 灵活性   | 高（运行时替换）     | 低（编译时确定）  | 高                 |
| 实现复杂度 | 中            | 低         | 中                 |
| 性能    | 中            | 高         | 中                 |

**采用原因**：
- 玩家控制与武器行为分离，职责清晰
- 便于添加新武器类型
- 支持武器切换时的状态保存与恢复

#### 决策7：武器吸血系统 ✅

**背景**：如何实现武器造成伤害时恢复玩家生命值的机制？

**现状实现**：
- **LifestealFeature**：独立的吸血特性类，支持等级升级
- **基础吸血比例**：1%
- **升级加成**：每级+1%吸血比例

**核心代码**：
```csharp
public class LifestealFeature
{
    public int Level { get; private set; } = 1;
    public float BaseLifestealPercent => 1f;
    public float LifestealPercent => BaseLifestealPercent + (Level - 1);

    public float GetLifestealAmount(float damage)
    {
        return damage * (LifestealPercent / 100f);
    }
}
```

**集成方式**：
```csharp
public abstract class WeaponBase : ViewController, IWeapon
{
    public LifestealFeature Lifesteal { get; set; } = new LifestealFeature();
    public bool IsBulletEnhanced { get; protected set; } = true;

    protected void ApplyLifestealToBullet(PlayerBullet bullet)
    {
        if (bullet != null)
        {
            bullet.lifestealPercent = GetLifestealPercent();
            bullet.isEnhanced = IsBulletEnhanced;
        }
    }
}
```

**采用原因**：
- 吸血逻辑独立封装，便于扩展和测试
- 支持武器等级升级成长
- 可灵活为任意武器添加吸血能力

## 5. 音效系统重构设计

### 5.1 现状问题

| 问题   | 描述                         | 影响     |
| ---- | -------------------------- | ------ |
| 代码重复 | 每把武器都有 30-50 行音效播放代码       | 维护成本高  |
| 资源浪费 | N 个武器 = N 个 AudioSource 组件 | 性能开销大  |
| 逻辑分散 | 音效逻辑分散在 6 个武器类中            | 难以统一管理 |
| 扩展困难 | 添加新音效需修改多个文件               | 易出错    |

### 5.2 重构目标

1. **集中管理**：创建 WeaponAudioManager 单例统一管理所有武器音效
2. **减少重复**：在 WeaponBase 中提供统一的音效播放方法
3. **资源优化**：全局使用 2-3 个 AudioSource，而非每武器独立挂载
4. **清晰分类**：区分循环音效（全自动）和单发音效（半自动/换弹）

### 5.3 目标架构

```
音效系统架构
├── WeaponAudioManager (单例，MonoBehaviour)
│   ├── loopSource (AudioSource)      // 循环音效：全自动武器持续射击
│   ├── oneShotSource (AudioSource)   // 单发音效：换弹、空挂、射击结束
│   └── reloadSource (AudioSource)    // 换弹音效（可选独立）
│
└── IWeapon/WeaponBase
    └── 音效配置数据
        ├── shootSounds (List<AudioClip>)
        ├── shootEndSound (AudioClip)
        ├── dryFireClick (AudioClip)
        └── reloadSound (AudioClip)
```

| `SingleShotStrategy`   | 手枪类   | 单发子弹   |
| `DoubleBarrelStrategy` | 霰弹枪升级 | 快速连射两次 |
| `SpreadShotStrategy`   | 霰弹枪   | 扇形散射   |
| `PiercingStrategy`     | 狙击枪升级 | 穿透多个敌人 |
| `BounceStrategy`       | 特殊武器  | 子弹反弹   |
