## 2. 模块划分说明

| 模块                   | 职责说明                                    | 划分理由                                                               |
| -------------------- | --------------------------------------- | ------------------------------------------------------------------ |
| **Global**           | 管理全局游戏状态（HP、经验、金币、等级、传承点），提供全局数据访问和操作接口 | 采用单例模式集中管理游戏核心数据，使用 BindableProperty 实现响应式更新，确保 UI 与数据实时同步，降低模块间耦合 |
| **PlayerController** | 负责玩家输入处理、移动、自动瞄准、武器切换和战斗逻辑              | 将玩家相关逻辑聚合，便于维护和扩展，武器系统通过接口 (IWeapon) 实现解耦                          |
| **EnemySystem**      | 管理敌人 AI 行为（追击、攻击、死亡），包含多种敌人类型           | 采用状态机模式实现复杂敌人行为，通过 IDamageable 接口统一伤害系统                            |
| **WeaponSystem**     | 管理武器切换、射击、换弹逻辑，支持多种武器类型                 | 定义 IWeapon 接口抽象武器行为，通过特性系统 (Features) 扩展武器能力，提高可扩展性                |
| **MapGenerator**     | 基于 BFS 算法生成程序化地图，管理房间布局和连接              | 将地图生成逻辑独立，便于调整地图算法和房间配置，支持动态门布局                                    |
| **WaveSystem**       | 管理敌人波次生成和难度递增                           | 实现动态敌人池机制，根据波次自动解锁更强敌人，控制战斗节奏                                      |
| **DropManager**      | 管理敌人掉落物生成（经验、金币、脏血、护盾、纯血）               | 集中处理掉落逻辑，便于调整掉落概率和物品类型，支持自动飞向玩家机制                                   |
| **PureBloodSystem**  | 管理纯血道具的飞射、追踪和拾取治疗逻辑                  | 将吸血效果转化为可拾取道具，增加操作手感和视觉反馈                                                 |
| **ShopSystem**       | 管理商店商品随机出货和购买逻辑                  | 提供金币消耗途径，增加游戏经济系统完整性                                                 |
| **MiniMapSystem**    | 管理小地图渲染、房间状态显示、玩家位置追踪                | 实时显示玩家周围房间，渐进式发现机制，增强探索体验                                           |
| **ShieldSystem**     | 管理护盾激活、保护期、格挡次数和碎裂逻辑                  | 提供临时伤害抵挡能力，保护期机制增加策略深度                                                 |
| **LifestealSystem**  | 管理武器吸血特性、等级升级、吸血量计算                   | 支持武器成长，增加战斗续航能力，丰富战斗策略                                                 |
| **UI 层**             | 管理游戏界面（主菜单、HUD、结算界面）                    | 遵循 MVVM 模式，通过 BindableProperty 实现数据驱动 UI 更新                        |

### 设计 1：框架选择 - 为什么使用 QFramework ✅

**背景**：作为独立开发者，希望在完成项目的同时，学习专业的游戏开发架构模式

**方案对比**：
| 维度 | QFramework | 原生 Unity |
|------|-----------|-----------|
| 架构规范 | 提供完整 MVC 架构 | 无强制规范 |
| 学习价值 | 可学习专业架构模式 | 从零摸索 |
| 开发效率 | 提供大量快捷工具 | 从零开始 |
| 代码质量 | 强制分层，结构清晰 | 易陷入混乱 |

**采用原因**：
- 提供完整 MVC 架构规范，帮助建立清晰的代码结构
- 提供 ViewController、Bind 等机制，减少样板代码
- 中文文档丰富，便于查找学习资源

### 设计 2：敌人行为 - 数据驱动设计 🔄

**背景**：初期尝试为每个敌人类型创建独立类（Enemy.cs、Enemy2.cs、Enemy3.cs），导致代码重复严重，维护成本高

**现状实现**：
- 将所有射击敌人的攻击逻辑集中到 `ShootingEnemy.cs` 中
- 通过 Inspector 暴露参数：攻击间隔、子弹速度、射击模式等
- 不同敌人变体通过调整 Inspector 参数实现，无需编写新代码

**方案对比**：
| 方案 | Inspector 参数配置（当前） | 独立类继承 | ScriptableObject 文件配置（计划） |
|------|------------------------|-----------|-------------------------------|
| 灵活性 | 高（实时调整） | 低（需改代码） | 高（配置即可改行为） |
| 开发效率 | 高（直接调参） | 低（需开发介入） | 中（需创建配置文件） |
| 扩展性 | 中（依赖代码暴露） | 低（需新增类） | 高（新增配置即可） |
| 复用性 | 中（场景内复用） | 低 | 高（跨场景复用） |

**采用原因**：
- 可通过 Inspector 直接调整敌人属性，无需编写代码
- 所有射击敌人共用一套攻击逻辑，减少重复代码
- 支持实时调整参数，便于快速迭代

**未来规划**：计划将参数文件化，使用 `ScriptableObject` 创建敌人配置模板，实现跨场景复用

> 详细重构过程见：[核心决策文档](file:///e:/unity/project/ProjectBlood/Technical%20Documentation/核心决策.md) 第1章「敌人系统设计」

### 设计 3：程序化地图生成 ✅

**背景**：如何实现游戏地图的多样性和可扩展性？

**方案对比**：
| 方案 | 程序化生成（BFS） | 预设地图 |
|------|-----------------|---------|
| 多样性 | 高（无限组合） | 低（有限关卡） |
| 开发成本 | 中（算法实现） | 高（逐个设计） |
| 可扩展性 | 高（调整参数即可） | 低（需重新设计） |
| 重玩价值 | 高 | 低 |

**采用原因**：
- BFS 算法确保地图连通性，避免死路
- 支持动态门布局，增加地图变化性
- 通过预测权重机制优化路径选择

| 扩展性 | 高（新增状态即可） | 低（需修改现有代码） |
| 维护成本 | 低 | 高 |
| 实现复杂度 | 中 | 低 |

**采用原因**：
- 状态机模式使敌人行为逻辑更清晰，每个状态职责单一
- 便于扩展新敌人类型和状态
- 状态切换逻辑集中管理，降低维护成本

### 设计 5：UI 数据绑定 - 响应式架构 ✅

**背景**：如何实现游戏状态变化时 UI 自动更新？

**方案对比**：
| 方案 | BindableProperty（响应式） | 传统事件回调 |
|------|--------------------------|------------|
| 代码简洁度 | 高（声明式绑定） | 低（手动订阅） |
| 维护成本 | 低（自动同步） | 高（需手动管理） |
| 可读性 | 高 | 中 |
| 技术一致性 | 与 QFramework 深度集成 | 独立实现 |

**采用原因**：
- BindableProperty 提供声明式的数据绑定，简化代码编写
- 自动处理状态变化通知，减少手动事件订阅代码
- 与 QFramework 框架深度集成，保持技术栈一致性

### 设计 6：全局状态管理 ✅

**背景**：如何管理跨场景的游戏数据（如传承点）？

**方案对比**：
| 方案 | PlayerPrefs + BindableProperty | 静态变量 |

| 响应式更新 | ✅ 支持 | ❌ 需手动实现 |

**采用原因**：
- PlayerPrefs 提供简单可靠的本地存储

### 设计 7：敌人系统美术表现与打击感 ✅

**现状实现**：
- **视觉反馈**：血液飞溅粒子、血迹残留、尸体飞散动画
- **物理反馈**：Collision 碰撞产生的击退效果
- **音效反馈**：受伤音效、攻击音效、激光持续音效
- **特效系统**：FxManager 统一管理特效实例化和生命周期

**核心决策**：
1. **血液飞溅系统**：随机角度、距离和缩放的血迹飞溅，模拟真实物理效果
2. **血迹残留**：死亡后留下血迹，增强战斗痕迹感
3. **尸体飞散效果**：沿受击方向飞出，增加战斗爽快感
4. **Collision 碰撞击退**：使用物理引擎实现受击击退（待优化为可控击退）
5. **激光蓄力指示器**：LineRenderer 宽度随蓄力进度递增，提供攻击预警
6. **音效分层设计**：受伤音效（0.5f）、射击音效（0.2f）等不同音量层次

> **设计变更**：原闪烁机制（红/白光）因受限于敌人本身颜色已废弃，改为血液飞溅+血迹残留+Collision击退

**详见**：《敌人系统设计文档 - 美术表现与打击感》

### 设计 10：护盾系统 ✅

**背景**：如何为玩家提供临时伤害抵挡能力？

**现状实现**：
- **ShieldState**：状态管理类，管理护盾激活状态、保护期和格挡次数
- **Shield**：道具类，定义初始格挡次数和保护期时长
- **保护期机制**：激活后一段时间内不消耗格挡次数

**核心机制**：
```
激活流程：拾取护盾 → 设置格挡次数(5次) → 启动保护期(5秒)
伤害处理：检测护盾 → 扣除格挡次数 → 保护期内不检查碎裂 → 非保护期且次数耗尽时碎裂
```

**实现特点**：
- **保护期设计**：护盾激活后有5秒保护期，期间受击不消耗格挡次数
- **音效反馈**：格挡和护盾碎裂均有独立音效
- **状态可视化**：通过ShieldSprite显示护盾激活状态

### 设计 12：纯血道具系统 ✅

**背景**：原来的吸血是直接给玩家加血，不够有"手感"，也缺少视觉反馈，想把吸血效果做成看得见摸得着的道具。

**方案对比**：
| 方案 | 直接回血（旧） | 纯血道具（新） |
|------|-------------|-------------|
| 视觉反馈 | 弱（几乎看不见） | 强（有飞射+追踪动画） |
| 操作手感 | 无 | 有拾取的爽快感 |
| 实现复杂度 | 低 | 中 |
| 策略深度 | 低 | 中（需要走位拾取） |

**核心机制**：
- **两阶段运动**：先从敌人身上飞溅出去，再转弯追踪玩家
- **数量拆分**：吸血量越大，生成的纯血道具越多（每5点治疗量多一个）

**实现特点**：
- **飞射阶段**：随机方向弹出，带阻尼减速
- **追踪阶段**：平滑转向追踪玩家，速度逐渐加快
- **视听效果**：多个小血球飞散再聚拢，及时反馈的拾取音效

> 功能说明见：[功能说明文档](file:///e:/unity/project/ProjectBlood/Technical%20Documentation/功能说明文档.md) 第7章「纯血系统」

### 设计 13：商店系统 ✅

**背景**：经济系统不完整，玩家无处消耗货币

**核心设计**：

- **购买流程**：靠近货架 → 显示购买按键提示 → 按F键购买 → 生成道具（金币不足时提示）

**商品价格表**：
| 道具 | 价格 | 说明 |
|------|------|------|
| 纯血 | 1金币 | 最便宜的回血道具 |
| 脏血 | 5金币 | 补充血库（弹药）资源 |

**实现特点**：
- **价格字段复用**：价格定义在 DropItem 基类里，商店不用单独维护价格表
- **售罄状态**：买完一次就不能再买了，避免无限刷
- **购买音效**：有专门的购买音效反馈

## 4. 关键设计模式总结

| 设计模式      | 应用场景                      | 实现效果      |
| --------- | ------------------------- | --------- |
| **单例模式**  | Global、DropManager、FxManager、MapController | 确保全局唯一访问点 |
| **状态机模式** | 敌人 AI 行为管理、纯血道具（Flying/Chasing） | 清晰的状态转换逻辑 |
| **策略模式**  | 武器系统（IWeapon 接口）          | 统一接口，灵活替换 |
| **观察者模式** | BindableProperty 数据绑定     | 自动响应状态变化  |
| **组件化模式** | 武器特性系统（LifestealFeature、GunClip） | 能力模块化组合   |
| **模板方法模式** | Enemy 基类定义受伤/死亡流程，子类可重写具体实现 | 代码复用，扩展性强 |
| **工厂模式** | FxManager 统一创建特效实例、DropManager 生成掉落物 | 集中管理，便于维护 |
| **组合模式** | BloodBank 与 WeaponBase 的集成 | 资源管理解耦 |
| **迭代器模式** | DynaGrid 遍历房间网格 | 简化网格访问 |
| **生产者-消费者模式** | BFS房间生成算法 | 高效的层级遍历 |
