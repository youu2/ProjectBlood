## 2. 模块划分说明

| 模块                   | 职责说明                                    | 划分理由                                                               |
| -------------------- | --------------------------------------- | ------------------------------------------------------------------ |
| **Global**           | 管理全局游戏状态（HP、经验、金币、等级、传承点），提供全局数据访问和操作接口 | 采用单例模式集中管理游戏核心数据，使用 BindableProperty 实现响应式更新，确保 UI 与数据实时同步，降低模块间耦合 |
| **PlayerController** | 负责玩家输入处理、移动、自动瞄准、武器切换和战斗逻辑              | 将玩家相关逻辑聚合，便于维护和扩展，武器系统通过接口 (IWeapon) 实现解耦                          |
| **EnemySystem**      | 管理敌人 AI 行为（追击、攻击、死亡），包含多种敌人类型           | 采用状态机模式实现复杂敌人行为，通过 IDamageable 接口统一伤害系统                            |
| **WeaponSystem**     | 管理武器切换、射击、换弹逻辑，支持多种武器类型                 | 定义 IWeapon 接口抽象武器行为，通过特性系统 (Features) 扩展武器能力，提高可扩展性                |
| **MapGenerator**     | 基于 BFS 算法生成程序化地图，管理房间布局和连接              | 将地图生成逻辑独立，便于调整地图算法和房间配置，支持动态门布局                                    |
| **WaveSystem**       | 管理敌人波次生成和难度递增                           | 实现动态敌人池机制，根据波次自动解锁更强敌人，控制战斗节奏                                      |
| **DropManager**      | 管理敌人掉落物生成（经验、金币、药水）                     | 集中处理掉落逻辑，便于调整掉落概率和物品类型                                             |
| **UI 层**             | 管理游戏界面（主菜单、HUD、结算界面）                    | 遵循 MVVM 模式，通过 BindableProperty 实现数据驱动 UI 更新                        |

## 3. 核心设计决策

> **状态说明**：✅ 已实施 | 🔄 进行中 | 📋 计划中

### 决策 1：框架选择 - 为什么使用 QFramework ✅

**背景**：作为独立开发者，希望在完成项目的同时，学习专业的游戏开发架构模式

**方案对比**：
| 维度 | QFramework | 原生 Unity |
|------|-----------|-----------|
| 架构规范 | 提供完整 MVC 架构 | 无强制规范 |
| 学习价值 | 可学习专业架构模式 | 从零摸索 |
| 开发效率 | 提供大量快捷工具 | 从零开始 |
| 代码质量 | 强制分层，结构清晰 | 易陷入混乱 |

**选择理由**：
1. **学习成长**：作为独立开发者，接触专业的游戏架构工具，提升技术能力
2. **快速开发**：提供 ViewController、Bind 等机制，减少样板代码，专注核心玩法
3. **代码规范**：QF 的 MVC 模式强制代码分层，避免后期代码混乱
4. **社区支持**：中文文档丰富，遇到问题易于查找解决方案

***

### 决策 2：敌人行为 - 数据驱动设计 🔄

**背景**：初期尝试为每个敌人类型创建独立类（Enemy.cs、Enemy2.cs、Enemy3.cs），导致代码重复严重，维护成本高

**现状实现**：
- 将所有射击敌人的攻击逻辑集中到 `ShootingEnemy.cs` 中
- 通过 Inspector 暴露参数：攻击间隔、子弹速度、射击模式等
- 不同敌人变体通过调整 Inspector 参数实现，无需编写新代码

**方案对比**：
| 方案 | Inspector 参数配置（当前） | 独立类继承 | ScriptableObject 文件配置（计划） |
|------|------------------------|-----------|-------------------------------|
| 灵活性 | 高（实时调整） | 低（需改代码） | 高（配置即可改行为） |
| 开发效率 | 高（直接调参） | 低（需开发介入） | 中（需创建配置文件） |
| 扩展性 | 中（依赖代码暴露） | 低（需新增类） | 高（新增配置即可） |
| 复用性 | 中（场景内复用） | 低 | 高（跨场景复用） |

**选择理由**：
1. **效率提升**：作为独立开发者，可通过 Inspector 直接调整敌人属性，无需编写代码
2. **减少重复**：所有射击敌人共用一套攻击逻辑，只需配置不同参数
3. **快速迭代**：实时调整参数，立即在场景中看到效果

**未来规划**：计划将参数文件化，使用 `ScriptableObject` 创建敌人配置模板，实现跨场景复用

***

### 决策 3：程序化地图生成 ✅

**背景**：如何实现游戏地图的多样性和可扩展性？

**方案对比**：
| 方案 | 程序化生成（BFS） | 预设地图 |
|------|-----------------|---------|
| 多样性 | 高（无限组合） | 低（有限关卡） |
| 开发成本 | 中（算法实现） | 高（逐个设计） |
| 可扩展性 | 高（调整参数即可） | 低（需重新设计） |
| 重玩价值 | 高 | 低 |

**选择理由**：
1. 程序化生成提供无限地图组合，提升游戏重玩价值
2. BFS 算法确保地图连通性，避免死路
3. 通过预测权重机制优化路径选择
4. 支持动态门布局，增加地图变化性

***

### 决策 4：敌人 AI - 状态机模式 ✅

**背景**：如何管理敌人复杂的行为逻辑（如 LaserEnemy 的追击→蓄力→发射状态切换）？

**方案对比**：
| 方案 | 状态机模式 | 条件分支（if-else） |
|------|----------|------------------|
| 逻辑清晰度 | 高（状态职责单一） | 低（逻辑混杂） |
| 扩展性 | 高（新增状态即可） | 低（需修改现有代码） |
| 维护成本 | 低 | 高 |
| 实现复杂度 | 中 | 低 |

**选择理由**：
1. 状态机模式使敌人行为逻辑更清晰，每个状态职责单一
2. 便于扩展新敌人类型和状态
3. 状态切换逻辑集中管理，降低维护成本
4. 符合开闭原则，新增状态无需修改现有代码

***

### 决策 5：UI 数据绑定 - 响应式架构 ✅

**背景**：如何实现游戏状态变化时 UI 自动更新？

**方案对比**：
| 方案 | BindableProperty（响应式） | 传统事件回调 |
|------|--------------------------|------------|
| 代码简洁度 | 高（声明式绑定） | 低（手动订阅） |
| 维护成本 | 低（自动同步） | 高（需手动管理） |
| 可读性 | 高 | 中 |
| 技术一致性 | 与 QFramework 深度集成 | 独立实现 |

**选择理由**：
1. BindableProperty 提供声明式的数据绑定，简化代码编写
2. 自动处理状态变化通知，减少手动事件订阅代码
3. 支持链式注册回调，代码更简洁
4. 与 QFramework 框架深度集成，保持技术栈一致性

***

### 决策 6：全局状态管理 ✅

**背景**：如何管理跨场景的游戏数据（如传承点）？

**方案对比**：
| 方案 | PlayerPrefs + BindableProperty | 静态变量 |
|------|-------------------------------|---------|
| 数据持久化 | ✅ 支持 | ❌ 不支持 |
| 响应式更新 | ✅ 支持 | ❌ 需手动实现 |
| 跨场景访问 | ✅ 支持 | ✅ 支持 |

**选择理由**：
1. PlayerPrefs 提供简单可靠的本地存储
2. BindableProperty 的 Register 回调机制自动同步数据到 PlayerPrefs
3. 支持游戏重启后数据恢复
4. 保持全局状态的响应式更新能力

***

### 决策 7：敌人系统美术表现与打击感 ✅

**背景**：如何提升敌人被攻击时的视觉和听觉反馈，增强战斗打击感？

**现状实现**：
- **视觉反馈**：血液飞溅粒子、血迹残留、尸体飞散动画
- **物理反馈**：Collision 碰撞产生的击退效果
- **音效反馈**：受伤音效、攻击音效、激光持续音效
- **特效系统**：FxManager 统一管理特效实例化和生命周期

**核心决策**：
1. **血液飞溅系统**：随机角度、距离和缩放的血迹飞溅，模拟真实物理效果
2. **血迹残留**：死亡后留下血迹，增强战斗痕迹感
3. **尸体飞散效果**：沿受击方向飞出，增加战斗爽快感
4. **Collision 碰撞击退**：使用物理引擎实现受击击退（待优化为可控击退）
5. **激光蓄力指示器**：LineRenderer 宽度随蓄力进度递增，提供攻击预警
6. **音效分层设计**：受伤音效（0.5f）、射击音效（0.2f）等不同音量层次

> **设计变更**：原闪烁机制（红/白光）因受限于敌人本身颜色已废弃，改为血液飞溅+血迹残留+Collision击退

**详见**：《敌人系统设计文档 - 美术表现与打击感》

## 4. 关键设计模式总结

| 设计模式      | 应用场景                      | 实现效果      |
| --------- | ------------------------- | --------- |
| **单例模式**  | Global、DropManager、FxManager 等全局管理器 | 确保全局唯一访问点 |
| **状态机模式** | 敌人 AI 行为管理（Chase/Wander/Shoot/Aim/Fire） | 清晰的状态转换逻辑 |
| **策略模式**  | 武器系统（IWeapon 接口）          | 统一接口，灵活替换 |
| **观察者模式** | BindableProperty 数据绑定     | 自动响应状态变化  |
| **组件化模式** | 武器特性系统                    | 能力模块化组合   |
| **模板方法模式** | Enemy 基类定义受伤/死亡流程，子类可重写具体实现 | 代码复用，扩展性强 |
| **工厂模式** | FxManager 统一创建特效实例 | 集中管理，便于维护 |
