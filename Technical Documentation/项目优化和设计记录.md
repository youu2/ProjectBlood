# 项目优化和设计记录

简单概括开发过程中比较重要的重构或设计，详细描述可参考具体细分文档

***

## 1. 敌人系统重构

### 设计背景

游戏需要多种类型的敌人，但是很多敌人的区别可能只是射击的频率，弹丸数，角度不同，但为每个敌人编写独立脚本开发效率低。

### 优化方案

整合现有敌人类型，状态机下沉到基类，将敌人按攻击方式初步分成三类，通过调整参数，用相同的脚本快速创建新敌人：

- **射击型敌人**（`ShootingEnemy`）：通过参数控制子弹数量、散射角度、连发间隔
- **激光型敌人**（`LaserEnemy`）：通过参数控制充能时间、伤害频率、多束激光，瞄准速度
- **近战敌人**（`MeleeEnemy`）：通过参数控制攻击间隔、攻击距离

**方案收益**&#x20;

- 新敌人和精英敌人开发成本低，逻辑直观，适配原型期快速迭代的节奏

* 解决了 “单敌人单脚本” 的代码冗余问题，同类型敌人复用率大幅提升

**局限权衡：** 继承式架构扩展性有限，新增攻击模式（如召唤师）必须新增子类，代码体量会随敌人类型线性膨胀，状态机逻辑固化，攻击逻辑与敌人实体强耦合, 玩家或复合型敌人无法复用。从项目规模看，当前规划内的全部敌人均可被三类攻击模式覆盖，新增全新攻击模式的需求频次极低，继承架构的膨胀风险在项目周期内完全可控。

## 2. 武器系统重构

### 设计背景

最初的 `IWeapon` 既未承担真正的接口职责，也未有效抽离通用逻辑，导致子类代码重复率高，系统职责混乱( 直接管理音效 )。    实际开发中发现，武器的核心逻辑高度相似，多数武器的差异仅集中在伤害、攻速等数值层面。

### 优化方案

将声音系统完全分离，并采用三层继承架构：

- **`WeaponBase`**：处理通用逻辑（弹药管理、换弹流程、吸血特性）
- **`AutomaticWeapon`**：全自动武器基类，统一实现连发射击逻辑（AK，MP5，Laser）
- **`SemiAutomaticWeapon`**：半自动武器基类，统一实现单发触发逻辑（AWP，DE，ShotGun）

### 二次优化：

进一步收敛同类武器的重复代码，将DE，AWP，AK，MP5 的核心攻击逻辑以及所有武器的大部分可配置属性完全整合进对应基类。这四个武器在场景内直接使用 **`SemiAutomaticWeapon`和**`AutomaticWeapon` 作为脚本, 无需再创建对应的武器脚本。

至此，武器系统实现了同类型变种武器的 0 代码快速配置。

**收益：**

- 彻底理清系统职责，解决初始版本的架构混乱
- 参数化配置支撑高频平衡迭代
- 继承链深度可控，逻辑链路直观清晰，无需理解复杂的组件依赖与组合关系

### 局限权衡：

该架构仍无法快速支持机制差异较大的复杂攻击模式；且攻击逻辑与武器实体强绑定，无法直接复用于敌人、炮台等其他攻击型实体，跨系统复用性弱于纯组合模式。从内容规划看，项目计划内的所有武器均能被全自动 / 半自动的分类完全覆盖，暂无大量特殊机制武器的开发计划，参数化架构的能力边界完全匹配当前需求。

## 3. 声音系统设计

### 设计背景

项目初期武器比较少，每个武器挂载独立的 `AudioSource` 播放音效，音效播放与武器 GameObject 生命周期强绑定。由于核心玩法支持开火过程中无缝切枪（取消射击后摇，通过武器切换实现类似”合轴“的伪多线输出模式，提升输出上限），所以当玩家在开火期间切换武器时，上一把武器的音效会突然中断，严重影响听觉体验。

### 初始方案与核心问题

初期尝试在切枪逻辑中增加延迟禁用、音效播放检测等补丁处理，试图保留音源直到音效播放完毕。但该方案本质是在错误架构上打补丁，带来三个核心问题：

- **逻辑耦合严重**：切枪业务逻辑与音频生命周期逻辑混杂，代码职责混乱，高频切枪场景下边界条件极多，bug 频发且难以定位；

&#x20;

- **资源利用率低**：每个武器独立持有音源，无法跨武器复用，场景内音源数量随武器数量线性增长，性能开销不可控；
- **通用能力缺失**：音源分散管理，无法实现全局音量统一控制、音效优先级调度等通用能力，后续扩展成本极高。

### 优化方案

使用集中式音频管理系统：

- 基于 QFramework 的 `AudioKit` 实现底层音频调度与音源对象池管理
- &#x20;

  封装 `AudioKitManager` 单例类，提供统一的播放、停止接口，同时通过 BindableProperty 与 PlayerPrefs 实现全局细分音量控制与设置持久化；
- 武器, UI 等业务仅负责调用播放接口，不直接持有、不管理底层 AudioSource 组件的创建与回收生命周期。循环类音效可持有框架返回的播放句柄，仅用于业务逻辑层面的启停控制，底层音源资源仍由音频系统统一调度与回收。

### 实现效果

- **彻底解决切枪音效截断问题:** 

  音效播放与武器 GameObject 生命周期完全解耦，切枪仅触发业务逻辑切换，已触发的音效会由音频管理器独立播放至结束，实现了无缝切枪的听觉平滑过渡，匹配核心玩法的体验目标。
- **提升音频播放性能与能力上限:**

  `AudioKit` 内置的 `AudioSource` 对象池实现了音源复用，避免了频繁创建销毁音源的性能开销；同时支持多音源并行播放，解决了单音源下高频射击导致的音效丢包问题，为后续高射速天赋等内容扩展提供了音频层支撑。
- **补齐全局音频管控能力:** 

  实现了音乐、音效双轨音量的统一调节与本地持久化，为后续设置面板开发预留了完整能力，无需再逐个修改业务侧代码。
- **系统职责解耦，可维护性提升:**

  武器系统彻底剥离音频管理职责，仅保留业务调用入口，符合单一职责原则；音频规则统一在管理器中维护，后续调整音频策略无需改动业务层代码。

### 局限权衡

- **框架依赖抬高深度定制成本：**

  底层基于 QFramework AudioKit 实现，核心调度、对象池、缓存逻辑均封装在框架内部，源码可改，但深度定制化（如自定义音效优先级调度、精细化 3D 空间音效衰减、自定义音频淡入曲线）需要修改框架源码实现，会增加后续框架版本升级的维护成本与兼容风险。
- **原生音量分层有限：**

  框架原生仅支持音乐、音效、人声三层独立音量管控，无法直接自定义新增细分通道（如 UI 交互音效、战斗音效、环境音效的独立音量调节）。
- 但是从需求规划看，项目暂无高度定制化的复杂音频需求，框架内置的播放、音量控制、对象池能力已完全覆盖当前与可预期的功能范围，架构快速解决了切枪音效截断、音源复用、全局音量管理的核心问题，武器系统与音频系统彻底解耦，大幅降低了音频开发成本。

## 4. 血库系统设计

### 设计背景

项目初期采用独立弹药库设计，每类武器对应专属弹药。但随着武器数量增加、无缝切枪的核心玩法落地，独立弹药体系的弊端逐步凸显：多武器轮换下玩家需要同时管理多套资源，认知负担过重；弹药耗尽直接强制停火的硬限制，会打断高频战斗的流畅节奏，与 “爽快射击” 的核心体验目标相悖。

### 初始方案与核心问题

&#x20;

独立弹药库的设计本质是传统射击游戏的资源逻辑，与本项目的多武器无缝切换玩法存在底层冲突：

- **玩家负担**：武器数量越多，资源管理成本越高，玩家需要额外关注多套弹药存量，分散战斗注意力，违背爽快感设计初衷；
- **平衡维度单一**：弹药仅作为输出的前置条件，无法与生存、天赋等系统形成联动，系统价值单薄，难以支撑 Roguelike 的流派差异化。

* **体验割裂**：弹药硬限制会直接中断输出节奏，与 “取消后摇、高频切枪保持输出” 的核心玩法设计目标矛盾；

### 优化方案

&#x20;

引入全局统一的 “脏血” 资源池，替代分散的独立弹药体系，构建「生存 - 输出」联动的资源循环系统。

#### 核心机制

1. **共用资源池**：所有武器共享同一套 “脏血” 资源，彻底消除多武器下的多资源管理负担；
2. **软性资源限制**：脏血耗尽后武器仍可正常射击，仅触发伤害衰减，从根源避免了资源耗尽导致的输出中断，保障高频战斗的流畅节奏。配套设计上，激光武器具备更高的伤害 / 脏血转化效率与稳定的基础输出，作为玩家脏血大量消耗后的低资源过渡选项，进一步平滑资源波动带来的体验落差。
3. **差异化消耗**：不同武器单次换弹消耗的脏血量不同，将资源消耗作为武器平衡的核心维度之一，强化武器定位差异。
4. **特殊换弹机制**：双击换弹键可触发特殊换弹，蓄力 3 秒后消耗脏血为所有未手持武器补满强化弹药。蓄力过程不干扰当前武器的普通攻击与常规换弹，但玩家主动发起攻击会立即中断蓄力。资源成本上，单次特殊换弹的脏血消耗高于单把武器的常规换弹，但低于逐一对所有武器执行常规换弹的总消耗，通过成本收益差引导玩家主动进行多武器轮换，贴合核心玩法设计目标。

#### 资源循环闭环

- **资源获取**：玩家受伤时自动补充脏血；血库存量低于阈值时，击杀敌人概率额外获得脏血奖励；鼓励玩家使用更激进的进攻策略
- **资源消耗**：换弹时消耗脏血强化武器伤害，将资源消耗与输出增益直接绑定；
- **资源转化**：脏血强化状态下击杀敌人，可回复玩家生命值，实现输出能力向生存能力的转化。

### 最终形成 **生命值 → 血库资源 → 伤害输出 → 生命值** 的完整闭环，让生存与输出形成互相转化的动态平衡。

### 设计价值

- 完美匹配核心爽点，保障战斗流畅性
- 简化资源管理，降低认知负担
- 构建玩法闭环，强化系统联动性
- 丰富平衡维度，支撑流派差异化

**局限**

**数值平衡复杂度上升：**系统同时耦合生命值、伤害、武器消耗、击杀回复四大变量，任意一处参数调整都会影响整个循环的收支平衡；且软性限制下不存在绝对的资源锁，伤害衰减比例，回复速率的调试容错空间小，容易出现 “资源溢出碾压” 或 “负向循环卡壳” 的极端情况，平衡调试成本高于传统硬限制弹药系统。

## 5. 玩家对象结构和动画

&#x20;

### 设计背景

最开始玩家和武器全是静态 Sprite，动作表现非常粗糙，打算补全角色动画和武器动效。

### 方案迭代

一开始想过两条路：要么补完整的逐帧动作，武器后坐暂时用纯程序动画实现，不做形变。但我绘制的素材基本都是 16×16 \~ 32×32 的小像素规格，试画了几帧腿部动作，很难在保持现有美术风格的前提下做出满意的效果，而且整套动作画下来美术量太大，性价比太低。

之后也考虑过骨骼动画：优势很明显，动画复用性强、资源体积小，调武器手感的时候直接拖骨骼就很直观；而且我也没打算靠锁帧数做复古质感，理论上骨骼能做出更顺滑的动作。不过同时我也了解了分层帧动画的方案，发现以我角色的复杂度（手脚都没有分段关节、武器是纯刚体、不需要权重形变），两者从拆 Sprite、搭层级到 K 关键帧的流程几乎一模一样，最终效果也没什么差别 —— 骨骼在这里基本就是一层没什么实际价值的中间抽象层。

既然效果差不多，分层帧还省了绑骨骼、刷权重的步骤，不用额外学新工具，最后就定了用分层帧动画；武器后坐也顺便统一走动画 Clip，不再单独写程序动画了，工作流更统一。

做动画的时候遇到个小问题：角色拆成好多部件之后，翻转朝向不能再像以前整图那样只翻一个 Sprite 了。最后选了最省事的方案：直接翻转整个 Player 根节点，对血条文字这类不能镜像的东西，单独再反一次缩放抵消掉。好处是以后加非对称的特效、附属物，只要挂在 Player 下面，都会自动跟着镜像，不用单独处理。

### 踩坑与解决方案

#### 问题 1：朝左开枪变成 “前坐力”

（朝右开枪后坐力动画正常，朝左开枪枪身反而往前冲。）

**分析**：武器后坐的 Transform 位移动画，和控制朝向的 `scale.x = -1` 水平镜像，都作用在了武器父节点这同一个对象上。负缩放会把节点本地的 X 坐标轴整个镜像反转，动画里预设的、指向枪托的后坐位移，朝左的时候就正好指向了枪口方向，变成了向前冲。

**试过的方案**：

- 反复检查角色和武器翻转逻辑是否出错，未找到根本原因
- 想过为向左射击添加一套镜像动画，但是工作量不小就先搁置了

#### 问题 2：后坐力动画的枪口上抬幅度被大幅削弱

**现象**：动画里 K 好的上抬角度，运行时只剩一点，几乎看不出来；挂机时武器的微摆动效果也几乎没了。

**分析**：还是类似的原因 —— 武器指向鼠标的逻辑，和后坐力的旋转动画，叠在了同一个节点上。瞄准逻辑是每帧 Update 都在覆写旋转，动画的旋转刚生效就被瞄准逻辑拉回去了，等于动画被持续抵消，自然就没效果了。

**试过的方案**：

1. 直接加大动画里的旋转角度：相当于硬抵消，效果很卡顿，完全没法用；
2. 开火后短暂禁用瞄准逻辑：手感很差，开枪的时候枪口完全不跟鼠标，体验很差；
3. 开火后降低瞄准的平滑跟随系数：效果不明显，而且很难预估实际抵消了多少，调参困难。

### 最终解决方案

说起来也很简单，就是在武器父节点外面再套一层叫 Arm 的空物体：把「武器跟随鼠标旋转」和「玩家整体镜像」这两件事，全都移到 Arm 节点上；原来的武器节点只负责播放后坐动画。

相当于用一层空物体把两类变换拆开了 —— 父层管基础朝向和瞄准，子层管动画偏移，两者是叠加关系，不会再在同一个节点上互相覆盖，两个问题同时解决了。

### 一点复盘

可惜没早点发现这么简单的结构问题，明明玩家身上已经在用 Whole Body 这种嵌套空物体的思路了，浪费了点时间。不过也是第一次正经做动画，印象更深了。说起来我一开始也没想到阿莫古斯小人能拆成这么多块，看到教程中生动的角色动画就尝试更细的拆分，btw，K 帧调动作还挺有意思的。
